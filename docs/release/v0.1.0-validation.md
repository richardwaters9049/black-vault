# Black Vault 0.1.0 — Validation Record

**Validated:** 1 October 2026
**Purpose:** Final engineering evidence for the portfolio/internal 0.1.0 milestone.
**Public distribution:** Not planned.

## Milestone position

Black Vault 0.1.0 is the completed portfolio milestone for the desktop architecture. It is not being published as a consumer security product. Release artefacts and CI evidence demonstrate cross-platform engineering and packaging rather than independently certified production security.

The `v0.1.0` tag was created from commit `7a7c1a094bddc34d1f94d3a2e87144e68e2ce6fd`. Subsequent `chore/code-audit-hardening` work performed the six-phase internal hardening programme and is the current portfolio code baseline.

## Cross-platform build evidence

The `Desktop cross-platform` GitHub Actions workflow has passed for macOS arm64 (DMG), Windows x64 (NSIS), and Linux x64 (AppImage and DEB).

The workflow runs frontend tests/build, Rust tests, strict Clippy checks and native Tauri packaging on each target. The application has also been exercised manually through its GUI on macOS. CI/package success is evidence of build portability; it is not represented as equivalent to full hands-on security acceptance on every OS.

## Final hardened test baseline

Phase Six completed with:

- **46/46 Rust tests passed**;
- **22/22 frontend tests passed**;
- TypeScript typecheck passed;
- Vite production build passed;
- strict Clippy (`-D warnings`) passed;
- Rustfmt check passed;
- production bundle contained no `VITE_DEV_VAULT_PASSWORD` reference;
- `npm audit` reported **0 known vulnerabilities**;
- RustSec `cargo audit` reported **0 vulnerability advisories** across 458 locked crate dependencies.

The Rust suite includes real subprocess interruption testing in addition to in-process fault injection.

## Final security finding

Phase Six identified one additional filesystem hardening opportunity: vault-header unlock performed a symlink metadata check followed by a separate read, leaving a small Unix check/use race.

The unlock path now uses the hardened bounded regular-file reader, including no-follow opening on Unix and validation of the opened file. The `unlock_rejects_a_symlinked_vault_header` regression test was added.

Commit: `bb06324 Security: reject symlinked vault headers`.

No Critical or High severity issue remained after the final audit.

## Dependency observations

RustSec produced three allowed transitive warnings rather than vulnerability findings: `proc-macro-error 1.0.4` is unmaintained; `glib 0.18.5` has an unsoundness warning; and `yoke-derive 0.8.3` is yanked. These are tracked through normal framework dependency maintenance rather than forced transitive overrides.

## Signing position

The macOS package is ad-hoc signed and is not Apple Developer ID signed or notarised. That limitation is acceptable for the project's current non-distribution purpose and must not be represented as production signing.

## Six-phase hardening programme

1. Error-handling hardening.
2. Decomposition of the former monolithic vault implementation.
3. Explicit separation of the legacy web architecture.
4. Production diagnostic/comment cleanup.
5. Test-noise and reliability cleanup.
6. Final security/code audit and symlink-header hardening.

This is the portfolio baseline. Core refactoring should stop unless a real defect or security issue is discovered.

## Evidence boundaries

This record supports claims about internal engineering, automated tests, CI packaging and the documented audit. It does **not** support claims that Black Vault is independently audited, third-party penetration-tested, formally verified, certified, or notarised for public macOS distribution.
